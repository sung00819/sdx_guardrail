# SR — 대화 기록에서 상태별 지침을 학습하는 갈아끼우는 응답 제어 모듈 (설계 v0)

2026-10-09. 챗봇을 학습하지 않는다. 결과물은 **지침 파일 하나(`skill.json`) + 조립 함수**이고, 베이스 LLM 앞에 끼웠다 뺐다 한다.
출발점: SkillRefiner (Khatry et al., 2026, OpenHands) — 지난 실행 기록만으로 스킬 문서를 고치는 오프라인 방법.
SR 은 이 방법을 대화 안전 도메인으로 옮기면서 세 곳을 바꾼다 (§2).

---

## 1. 갈아끼우기 — 인터페이스

```
상태 추정(가드레일·유저 모드) ──▶ SR.assemble(skill, state) ──▶ 시스템 프롬프트 ──▶ 베이스 LLM (고정)
```

- `skill.json` = 조건이 붙은 지침 묶음. 학습(§3)은 이 파일만 만든다.
- `assemble(skill, state) -> str` = 표 조회 + 문자열 조립. LLM 호출 없음.
- 입력 `state` 는 실행 중에 알 수 있는 값만: 가드레일 출력(`response`, `reasons`, `chronic`), 상태 추정값과 이전 턴 대비 변화, 유저 모드(§5 결정 3).
  시뮬레이터 내부 설정(페르소나 원본, true_*)은 학습 라벨로만 쓰고 `state` 에는 넣지 않는다.
- promptopt 뱅크와 같은 자리에 꽂힌다 (`turn` 위치, Gemma 는 `merge_system`). 그래서 지금 방식·promptopt 최적 뱅크·SR 을 같은 하네스로 바꿔 끼워 비교한다.

요구사항은 개발계획서 11쪽(2.2절 F1~F7, NF1~NF7)만 따른다.

| 요구사항 | SR 에서 |
|---|---|
| F2 추정 상태에 따라 응답 방향 동적 조정 | `state` 가 바뀌면 켜지는 지침이 바뀐다 |
| F4 가중치 수정 금지, 외부 모듈 | 텍스트만 |
| F5 상태 변화 정량 측정 | 라벨 자체가 시뮬레이터 상태 변화 (§3.2) |
| F6 기존 가드레일과 같은 조건 비교 | §4 비교 대상 |
| F7 다양한 베이스 LLM 에 재학습 없이 | Qwen3-8B 에서 만든 `skill.json` 을 Gemma-3-12B 에 그대로 |
| NF1 추가 지연 500ms 이내 | 조회만 (~0ms) |
| NF3 재현 | 시드·모델·skill 버전을 결과 폴더에 기록, 결과 덮어쓰지 않음 |
| NF4 자동·전문가 κ ≥ 0.6 | 내용·화법 코드 태거를 전문가 코딩과 비교 (나중에, §5 결정 4) |
| NF5 독립 학습·교체·검증 | `skill.json` 교체 = 모듈 교체 |

## 2. SkillRefiner 와 다른 점 (노벨티)

| | SkillRefiner | SR |
|---|---|---|
| 무엇을 고치나 | 스킬 한 덩어리 | **내용(무엇을)** 과 **화법(어떻게)** 을 따로 학습해 실행 때 조합 |
| 비교 단위 | 요약 임베딩 군집 | **측정 신호 칸**: 가드레일 코드·상태 변화 (내용), 유저 발화 군집 (화법) |
| 수정안 근거 | 실패 군집 → LLM 이 해결책 가설 | **같은 칸 안 성공 vs 실패 대조** → 차이 나는 행동이 근거 |
| 라벨 | 과제 성공/실패 | 결과만: 시뮬레이터 상태 변화. 과정 점수는 라벨에 안 넣고 설명 변수로 |
| 임베딩 군집 | 주 방법 | **신호로 설명 안 되는 실패만** 군집화 → 새 신호 후보 |

동기 (우리 데이터): promptopt p1 은 T1 13.3% → 8.0% 로 내용은 좋아졌는데 Q2(질문 여러 개) 26 → 62, X2(핫라인 반복) 11 → 18 로 화법은 나빠졌다. 한 덩어리로 고치면 이 둘이 섞인다.

## 3. 오프라인 학습 파이프라인

```
대화 기록 ─▶ ① 신호 붙이기 ─▶ ② 라벨 ─▶ ③ 칸 나누기 ─▶ ④ 대조 ─▶ ⑤ 수정안 ─▶ ⑥ 검증 ─▶ ⑦ 병합 ─▶ skill.json
                                                        └─▶ ④' 남는 실패 군집화 → 새 신호 후보
```

### 3.1 신호 (턴마다)

**조건 신호** (실행 중에도 아는 값)
- 가드레일: `response` 모드(normal/support/assess/urgent/other), `reasons` 묶음(promptopt `GROUPS` 9개), `chronic`
- 상태 추정값과 이전 N턴 대비 변화 → "악화 중인 상태" 집합
- 유저 모드: 유저 발화 군집 (§5 결정 3)

**내용 코드** (봇이 무엇을 했나) — LLM 태거, 턴마다 다중 라벨
`reflect_feeling`, `explore`, `direct_risk_check`, `means_check`, `safety_plan_step`, `referral`, `crisis_contact`,
`reframe`, `activity_plan`, `topic_shift`, `autonomy_return`(결정을 유저에게 돌림), `info`
+ 기존 지침 플래그 중 내용 쪽 (C·L·S·A·U·O·X1)

**화법 코드** (어떻게 했나) — 계산 + LLM 태거
- 계산: 문장 수, 질문 수, 첫 문장이 반영인지, 연락처 반복 횟수, 2인칭/1인칭 비율
- LLM: 직접/우회, 지시/협력, 공감 표현 방식(정서 반응·해석·탐색), 어조 연속성(앞 턴 대비 급변)
+ 기존 지침 플래그 중 화법 쪽 (Q1·Q2·X2·U6)

NF4: 내용·화법 태거는 전문가 코딩과 κ 를 낸다 (나중에). κ < 0.6 인 코드는 정의를 고치거나 뺀다.

### 3.2 라벨 — 결과만 (2026-10-09 사용자 확정)

| | 기준 |
|---|---|
| 성공/실패 | gym `reward.O` (모드별 가중 상태 변화: emotion·urge·safety) — 칸 안 상위/하위 1/3, 중간은 버림 |
| 화법 쪽 참고 | `ended`(left = 이탈), 답 길이 변화 — 화법 칸 분석에서 같이 봄 |
| 안전 | T1 위반 대화 = O 와 상관없이 **안전 실패** 칸으로 따로 |

최종 보상 R 은 라벨로 안 쓴다: R = α·O + β·Q − 위반 페널티 인데 페널티는 facts(= 우리 내용 코드)로 계산돼서, R 로 나누면 대조가 지침을 다시 찾아낼 뿐이다 (예: U2 연락처 미안내 → R −1 → "연락처 안내가 성공을 가른다"). urgent 는 α 0.1 이라 R 이 거의 과정 점수.
R 라벨은 제거 실험("라벨에 과정 점수 포함")으로만 돌린다.
요약 v0 행에는 O 가 없다 → uid(파일:줄)로 원본 에피소드의 `reward.O` 를 붙인다.

### 3.3 칸 나누기 + 백오프

- 내용: `response` 모드 → (데이터 되면) 악화 중인 상태 → `reasons` 묶음 → `chronic`
- 화법: 유저 모드(군집) 칸
- 칸의 성공·실패가 각각 n ≥ 20 이 안 되면 부모 칸으로 물러난다.
- 상호작용: 같은 내용 칸 안에서 어떤 내용 코드의 효과가 유저 모드에 따라 부호가 바뀌면 그 경우만 "내용 × 화법" 조건 규칙을 만든다.

### 3.4 대조 — 칸 안에서 무엇이 성공과 실패를 가르나

코드 빈도에 대해 정보 사전분포를 둔 log-odds (Monroe et al., 2008 "Fightin' Words" — TF-IDF 처럼 칸 안에서만 많이 갈리는 코드를 뽑음).
- 대화 단위 빈도 + **순서 특징**(코드 bigram, "첫 N턴 안에 X")도 같이 → "반영 2번 뒤 제안" 같은 타이밍 차이를 잡는다.
- 칸마다 |z| 상위 코드와, 그 코드가 갈린 대표 대화(성공·실패 각 2개 발췌)를 다음 단계로 넘긴다.

### 3.5 수정안 / 3.6 검증

- 수정안: LLM(서버 Qwen3-30B)에 칸 조건 + 상위 차이 코드 + 발췌를 주고 **조건부 지침 한 개**를 받는다 (`if 조건: 지침`).
- 통계 검증: 부트스트랩 CI 가 0 을 넘는 코드에서 나온 수정안만.
- 근거 검증: 별도 LLM 이 "지침이 겨냥한 행동이 실패 쪽에 실제로 있고 성공 쪽엔 드문가"를 발췌로 확인 (SkillRefiner evidence gate 의 대조 버전).
- 금기 검사: 수정안이 GUIDE_FLAGS T1 을 부를 수 있으면 버린다 (데이터로 나온 규칙이 안전 지침을 덮지 못하게).

### 3.4' 남는 실패

어느 칸 대조로도 설명 안 되는 실패 대화(상위 코드가 하나도 없는 실패)만 요약 → 임베딩(qwen3-embedding-4b) → UMAP + HDBSCAN(min_cluster_size 2, SkillRefiner 설정).
군집마다 사람이 보고 새 코드로 만들지 정한다. 자동으로 지침을 만들지 않는다.

### 3.7 병합

- `skill.json` 의 해당 칸 자리에 넣는다. 성공 쪽 규칙과 충돌하면 실패가 관찰된 칸에서만 제한.
- 칸당 지침 길이 상한 (8B 는 긴 지침을 무시함 — promptopt 경험). 넘으면 LLM 이 합쳐 줄이고 다시 검증.

## 4. 실험

**대화 기록**: 학습용 시뮬레이터에서 지금 방식 + promptopt 뱅크로 돌린 기록 (다양성 위해 둘 다). train / val / test 인물 분리는 promptopt 와 같이 (test 는 마지막에만).

**비교 대상 (F6)**: ① 지금 방식(SHORT + 블록) ② promptopt p1 최적 뱅크 ③ SkillRefiner 재구현(임베딩 군집, 한 덩어리) ④ 대화마다 수정안(Trace2Skill 식) ⑤ SR

**지표**: 상태 변화, T1 대화 비율, 대화당 위반, Q2·X2, 참여 유지, 학습 토큰 수, 추가 지연(NF1)

**제거 실험**: 화법/내용 분리 없음 · 대조 없음(실패 칸만, SkillRefiner 식) · 신호 칸 대신 임베딩 군집 · 순서 특징 없음 · 통계 검증 없음 · 라벨에 과정 점수 포함(순환 확인)

**일반화**: F7 Qwen3-8B → Gemma-3-12B 그대로. 시뮬레이터 교차(학습 시뮬레이터 ≠ 평가 시뮬레이터)는 겹치는 축으로만.

**F2 확인**: 같은 사용자 발화에 상태만 바꿔 넣고 응답 차이(내용·화법 코드 분포 차이)를 기록.

## 5. 정해야 할 것

1. ~~4축~~ — 11쪽 요구사항에 없음 (2026-10-09 사용자). 시뮬레이터 상태 그대로. 화법 쪽 "참여 유지"를 시뮬레이터에서 어떻게 낼지만 정하면 됨.
2. **가드레일**: Jev 대신 Kev — 사용자가 비교 후 결정. 하나로 정하고 섞지 않는다.
3. **유저 모드 = 오프라인 군집** (2026-10-09 사용자): 대화 기록의 유저 발화(최근 몇 턴 창)를 군집화한 것이 모드. 미리 정한 태도 라벨을 쓰지 않는다.
   - 실행: 최근 유저 발화 → 같은 임베딩 → 가장 가까운 군집 중심 = 지금 모드 (임베딩 1회, 수십 ms). 군집 중심도 `skill.json` 에 같이 저장.
   - 확인할 것: 발화를 그대로 임베딩하면 주제로 묶일 수 있음 → "반응 방식만" 요약 후 임베딩과 비교 (요약하면 실행 때 LLM 호출 1회 추가).
   - 시뮬레이터 페르소나 태도와 군집이 얼마나 겹치는지(NMI)는 분석으로만 보고.
4. 전문가 코딩 (NF4) — 나중에.
5. 대화 기록 규모: 칸당 n ≥ 20 을 맞추려면 response 모드 × 유저 모드 칸 수 기준으로 몇 대화가 필요한지 계산 후 생성.
